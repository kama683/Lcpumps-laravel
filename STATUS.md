размера (8 МБ), magic bytes (переиспользован `FileSignatureVerifier` из

`storage:link` нужен — см. `DEPLOY.md`), санитизация slug. Сознательно
отдельный сервис от приватных вложений этапа 6 (разные лимиты/диски/типы).

Заявки: список с фильтром `?status=`, карточка с авто-переходом
`new → read`, технические поля в каноническом порядке (тот же список
констант, что и в письме этапа 6), удаление с очисткой файлов вложений с
диска (путь читается до удаления строки — каскад в БД не трогает диск).

Скачивание вложений (`GET /api/admin/attachments/{id}`): `Storage::disk('local')->download()`
— стриминг через `fpassthru()`, не читает файл в память; отдельные 404 для
"нет записи в БД" и "есть запись, файла на диске нет"; `Content-Disposition`
с `filename*=UTF-8''<percent-encoded>` для кириллицы (плюс ASCII-fallback,
которого не было в исходнике — не поведенческое отличие, чистое
надмножество, браузеры это давно поддерживают).

Каскад секций (проверено, не реализовывалось — в исходнике админки для
секций нет и здесь тоже нет): `products.section_id` — `ON DELETE SET NULL`,
`section_translations.section_id` — `ON DELETE CASCADE` на саму секцию.
Если секция когда-либо будет удалена (сейчас только через `tinker`/будущий
функционал), её товары не удаляются, просто теряют `section_id` и попадают
в резервную группировку по `category` — `sort_order` при этом не
пересчитывается и может оказаться не строго последовательным внутри новой
группы (не баг, просто не гарантирована плотная нумерация после такого
события).

25 новых тестов (см. раздел 3), полный прогон — 72 passed / 1 unrelated
failed на SQLite, 72/72 на реальном MySQL (см. раздел 3).

## 4. Расхождения и риски

**Прежний главный риск (этапы 6–7 не закоммичены) снят** — оба этапа
закоммичены отдельными коммитами (`93b45a3`, `aeb5982`), пути перечислены
явно, `git add -A` не использовался ни разу. Этап 8 на момент записи всё
ещё в рабочем дереве — тот же риск актуален для него, пока не
закоммичен следующим шагом.

**`public/build/` — общий генерируемый артефакт, коммитить которого по
отдельным сессиям не получится чисто.** Первая сессия (батч 4, about-us/
faq/news/services/solutions) на момент этой записи тоже держит
несохранённые изменения в `resources/css/js` + свои Blade-шаблоны, и её
последняя пересборка `public/build/` тоже не закоммичена. Tailwind
компилирует ОДИН файл со всеми классами, встреченными во ВСЕХ
Blade-шаблонах разом — в отличие от PHP-файлов, "чья" часть CSS в
скомпилированном бандле не определить и незачем: он всегда отражает
полное текущее состояние дерева, а не чей-то один этап. Пересборка,
сделанная для этапа 8 (`npm run build`, см. раздел 3), поэтому уже
включает и незакоммиченные Blade/CSS-правки первой сессии — это ожидаемо
и не ошибка, но если решите коммитить `public/build/` вместе с этапом 8,
имейте в виду, что коммит формально "потащит" за собой стили ещё не
закоммиченных публичных страниц батча 4. Альтернатива — оставить
`public/build/` не закоммиченным до координированной финальной сборки
(этап 10), собрав его тогда одним разом поверх уже смерженной работы
обеих сессий.

**Прямых конфликтов на уровне строк кода не обнаружено.** Батчи 1–3 (эта
сессия) и работа второй сессии не редактировали одни и те же файлы
одновременно — пересечение только на уровне "читал, но не менял"
(`bootstrap/app.php`, `routes/web.php` — обе стороны знают об их текущем
содержимом, но правки не перекрываются построчно).

**Общие файлы, которые каждая сторона меняла независимо:**
- `routes/web.php` — вторая сессия добавила `POST /contact` и весь блок
  `/admin`+`/api/admin`; эта сессия ничего в нём не меняла в батчах 1–3
  (все нужные маршруты уже существовали с этапа 4).
- `config/auth.php` — полностью переписан второй сессией под единственный
  guard `admin`. Эта сессия нигде не использует `Auth`/guards, конфликта
  по использованию нет.
- `composer.json`/`composer.lock`, миграции — не менялись ни той, ни другой
  стороной за пределами того, что уже было закоммичено к этапу 3.

**Контракт формы заявки — проверен, сходится.** Docblock
`ContactController::submit()` заявляет точный список имён полей; сверено
построчно с фактическим чтением полей в `ContactSubmissionHandler::handle()`
— совпадает:
- honeypot: `website`
- основные: `name`, `email` (обязательные), `company`, `phone`, `message`
- режим: `mode` = `basic` | `technical`
- технические (основные): `model`, `flow`, `head`, `power`, `speed`,
  `efficiency`, `temperature`, `inlet_diameter`, `outlet_diameter`,
  `pump_material`
- технические (доп.): `motor`, `voltage`, `protection_level`,
  `cooling_method`, `motor_efficiency`, `weight`
- вложения: `attachments[]` (обязательно со скобками — иначе PHP не
  распарсит массив файлов)
- route: `POST contact.submit` (+ `loc.contact.submit` для kk/en/zh), `@csrf`

Вывод ошибок — двухпутевой, и **страница `/contact` (батч 5, ещё не
построена) должна поддержать оба пути**:
1. обычная ошибка — `$errors->first('contact')` (один общий ключ `contact`,
   не по каждому полю отдельно), плюс `old()` для всех текстовых полей
   (вложения не восстанавливаются — файлы не переживают редирект);
2. превышение `post_max_size` на уровне PHP (до того, как Laravel вообще
   увидел запрос) — редирект с `?contactFormError=...` в query-строке,
   уже переведённым текстом; `old()` в этом случае тоже теряется, это
   ограничение PHP, не контроллера.

Оба пути покрыты тестами (`test_missing_required_fields_returns_error...`,
`test_post_too_large_redirects_with_translated_query_param` и т.д.) — но
только на уровне HTTP-запроса к контроллеру, не через реальную форму в
браузере, потому что Blade-разметки `/contact` ещё нет.

**Прочие находки, не конфликты:**
- `tests/Feature/ExampleTest.php` — штатный тест из Laravel-скелета (этап 1),
  не относится к работе ни одной из сессий. Падает, потому что бьёт `GET /`,
  а `HomeController` теперь зависит от таблицы `products`, которой в
  дефолтном sqlite-тестовом окружении без `RefreshDatabase` нет. Единственный
  красный тест в проекте.
- `SESSION_LIFETIME` в `.env.example` изменён с 120 (2 часа, Laravel-дефолт)
  на 10080 (7 дней) — это глобальная настройка Laravel, влияет на любые
  будущие сессии, не только на admin-guard, так как в Laravel нет
  per-guard TTL. Сейчас безвредно (единственный guard — `admin`), но при
  добавлении любой другой сессионной функциональности на публичной части
  это стоит держать в уме.
- Файл `KNOWN_DEFECTS.md` создан этой сессией (батч 3) уже после последних
  изменений второй сессии — стоит убедиться, что автор второй сессии тоже
  о нём знает, прежде чем писать в него дальше.

## 5. Известные дефекты

Полный текст — `KNOWN_DEFECTS.md` в корне репозитория. Ниже — сведённое

`text-[clamp(30px,4vw,48px))]` — лишняя закрывающая скобка, ломает

### Дефект 2 — контент и `<title>` не локализуются на нескольких страницах

Источник вызывает `getApplicationsCards()`/`getCompanyParagraphs()` без
аргумента локали (дефолт `"ru"`), на трёх страницах вдобавок статический
`export const metadata` вместо `generateMetadata()`. Подробная таблица
затронутых страниц/полей — в `KNOWN_DEFECTS.md` (найдено в батче 3):

`/services`, `/faq`, `/contact` (только контент), `/about-us` (только
`<title>`).

**Статус:** сохранено как есть в порте для уже построенных страниц
(`ApplicationsController`); при построении `/services`/`/faq`/`/contact`/
`/about-us` в батче 4/5 та же логика (вызов без локали) будет
воспроизведена намеренно, для совпадения с живым сайтом.

**По вашему указанию: перевод недостающих строк больше не блокер** — вы
пишете их сами, а не ждёте заказчика. Далее — точный список того, что

## 6. Блокеры

**Версия PHP на хостинге — не подтверждена.** `composer.json` требует
`"php": "^8.3"` (используется PHP 8.3 синтаксис — typed class constants).
`DEPLOY.md` уже фиксирует это как блокер: нужно проверить Plesk →
Domains → PHP Settings → выпадающий список версий на реальном тарифе
PS.kz, прежде чем начинать деплой (этап 10). Если доступен только 8.2 или
ниже — блокирует весь проект, а не только этап 10.

**Незакоммиченная работа этапа 8** — не блокер для продолжения этапа 5,
но тот же класс риска, что раньше был у этапов 6–7 (раздел 4), до
следующего коммита.

**Переводы — не блокер** (см. раздел 5, по вашему указанию).

**Для продолжения этапа 5 (батчи 4–5) блокеров не обнаружено** — все
зависимости (`App\Support\Content`, `CatalogService`, языковые файлы)
уже на месте или расширяемы по образцу батча 3.
